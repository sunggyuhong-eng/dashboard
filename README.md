# 콩스튜디오 채용 대시보드

> 이 저장소는 대시보드 전용 소스만 빌드합니다. 이전에 `gpt-final` 파일을 함께 업로드했다면 `src/analysis.ts`, `src/analysis.test.ts`, `src/data.ts`, `src/pagination.ts`, `src/pagination.test.ts`를 삭제하세요. 최신 빌드 설정은 남아 있는 미사용 파일을 컴파일 대상에서 제외합니다.

원본과 `IMPORTRANGE`로 연결된 대시보드 전용 사본에서 TO와 지원자 진행 단계를 읽어 GitHub Pages에 표시하는 읽기 전용 대시보드입니다.

## 주요 기능

- 연동용 사본의 `Dashboard_TO`와 `Dashboard_지원자` 탭을 매시간 자동 반영
- 직전 동기화 이후 새로 생긴 공고에만 `NEW` 표시하고 다음 동기화에서 자동 해제
- 메인 상단에는 오픈 공고, 목표 TO, 진행 지원자 3개 핵심 지표만 표시
- 오픈 공고 아래의 단일 `채용 운영 요약`에서 프로젝트별 채용 비중과 전형 흐름을 함께 표시
- 코딩테스트 → 면접 전체 → 처우협의 → Offer 진행 인원을 연결된 흐름으로 요약
- 채용 현황을 `프로젝트 | 채용 직무 | 목표 TO | 채용 배경 | 현재 진행` 표로 표시
- `Octopus`, `Project Octopus`, `OTPS` 프로젝트 표기는 메인에서 `OTPS`로 통합
- 메인에서는 공고 상세 표를 제거하고 프로젝트 요약에 집중
- `리포트 생성하기`에서 표지, 전체 요약, 전형별 인원, 오퍼·입사 예정 및 프로젝트별 진행 현황을 PDF로 저장
- 목표 TO와 채용 배경은 시트에서 불러오고, 자유 메모와 전형 표시 설정만 현재 브라우저에 저장
- 아트·개발 직무에 맞는 전형 단계를 자동 추천하고 공고별로 사용 단계를 선택
- 공고별로 9개 진행 단계의 지원자 확인
- Offer 지원자의 입사 예정일을 채용 현황과 지원자 카드에 표시
- 오른쪽 아래 면접 일정 달력에서 프로젝트별 1차·2차 면접 확인
- 대시보드 화면과 읽기 API는 기존 채용 시트를 수정하지 않음
- 고정 비밀번호 로그인 화면과 세션 단위 로그아웃 제공

표시 단계: `온라인 과제`, `코딩테스트`, `역량검사`, `면접`, `1차 면접`, `2차 면접`, `면접합격`, `처우단계`, `Offer`

`Hired`, 불합격, 포기, 취소 등은 카드에서 제외합니다. `Hired`는 충원 완료 인원 계산에만 사용합니다.

## 비밀번호 잠금

- 사이트에 접속하면 비밀번호 입력 화면이 먼저 표시됩니다.
- 인증 상태는 현재 브라우저 탭에서만 유지되며 탭을 닫거나 로그아웃하면 다시 입력해야 합니다.
- GitHub Pages의 정적 비밀번호 잠금은 일반 방문자의 화면 접근을 막는 용도입니다. `dashboard.json`을 포함한 배포 파일을 서버 수준에서 비공개로 만드는 기능은 아닙니다.

## 데이터 흐름

1. 연동용 사본이 `IMPORTRANGE`로 원본의 필요한 열만 가져옵니다.
2. Apps Script가 사본의 `Dashboard_TO`, `Dashboard_지원자` 탭을 읽어 반환합니다.
4. GitHub Actions가 프로젝트명과 공고명을 기준으로 공고와 지원자를 연결합니다.
5. `Dashboard_TO`에 있는 공고만 현재 오픈 공고로 표시합니다.
6. 결합 결과를 `dashboard.json`으로 만든 후 GitHub Pages에 배포합니다.
7. 대시보드는 배포된 JSON을 기본으로 읽으며 원본 시트에는 아무것도 쓰지 않습니다.

사이트에 접속하거나 새로고침하면 Apps Script의 읽기 전용 API에서 최신 데이터를 자동으로 받아 표시합니다. 상단의 `데이터 다시 불러오기`도 Cloudflare나 GitHub Actions를 거치지 않고 같은 방식으로 현재 화면을 즉시 갱신합니다. 정식 배포 데이터는 기존대로 매시간 7분 GitHub Actions가 갱신하며, Apps Script를 일시적으로 불러오지 못할 때만 마지막 배포 데이터를 대신 표시합니다.

지원자 이름과 진행 단계는 배포 결과의 JSON에 포함됩니다. 로그인 없는 GitHub Pages를 사용하므로 사이트 주소를 아는 사람은 이 데이터를 볼 수 있습니다.

## 1. 별도 GitHub 저장소 만들기

1. GitHub에서 새 저장소를 만듭니다.
2. 저장소 이름을 `kong-recruiting-dashboard`로 입력합니다.
3. ZIP 내부의 모든 파일과 폴더를 저장소 최상단에 업로드합니다.
4. 저장소 `Settings → Pages → Build and deployment`에서 Source를 `GitHub Actions`로 선택합니다.

저장소를 Private으로 설정해도 배포된 GitHub Pages 사이트의 공개 여부와는 별개입니다.

## 2. Google Apps Script 설치

1. 연동용 `채용 대시보드 시트`를 엽니다.
2. `확장 프로그램 → Apps Script`를 선택합니다.
3. 기존 `Code.gs` 전체를 ZIP의 `google-apps-script/Code.gs` 내용으로 교체합니다.
4. `프로젝트 설정 → 스크립트 속성`에 `API_TOKEN`을 등록합니다. 값은 직접 만든 40자 이상의 임의 문자열입니다.
5. `배포 → 배포 관리 → 수정`에서 새 버전으로 웹 앱을 배포합니다.
6. 실행 사용자는 `나`, 액세스 사용자는 `모든 사용자`로 설정합니다.
7. `/exec`로 끝나는 웹 앱 주소를 복사합니다.
Apps Script는 연동용 사본의 다음 탭만 읽습니다.

- 지원자: `Dashboard_지원자`
- 공고: `Dashboard_TO`
- 지원자 추이 탭은 API가 읽지 않으며, 기존 Gmail 라벨이나 시트 탭은 이 ZIP에서 생성·수정·삭제하지 않습니다.

지원자 시트에서 필요한 헤더는 `진행단계`, `이름`, `직무(공고명)`입니다. `PJ` 열이 있으면 프로젝트명으로 사용합니다. `입사 확정 날짜`, `1차 면접 날짜`, `2차 면접 날짜` 열은 Offer 입사 예정일과 면접 캘린더에 사용합니다.

원본의 B·D·F·H·X·P·S열을 지원자 사본의 A:G열에 행이 어긋나지 않게 가져오려면 `Dashboard_지원자`의 기존 수식을 아래처럼 교체합니다.

```text
=CHOOSECOLS(IMPORTRANGE("원본 스프레드시트 URL","'1. 2026 Interviewee'!A:X"),2,4,6,8,24,16,19)
```

이 결과는 `진행단계 | 이름 | PJ | 직무(공고명) | 입사 확정 날짜 | 1차 면접 날짜 | 2차 면접 날짜` 순서가 됩니다. 처음 연결할 때 `#REF!`가 표시되면 `액세스 허용`을 누릅니다.

`Dashboard_TO` 시트는 다음 순서로 관리합니다.

| 열 | 데이터 |
|---|---|
| A | 프로젝트 |
| B | 공고명 |
| C | 채용인원 |
| D | 채용사유 |

`Code.gs`의 대시보드 API는 읽기 전용이며 원본 채용 시트와 `Dashboard_TO`·`Dashboard_지원자`를 수정하지 않습니다. 이전 버전이 만든 `채용대시보드_공고` 탭은 새 코드를 배포한 후 삭제할 수 있습니다. 기존 Gmail 수집 트리거가 켜져 있다면 Apps Script의 트리거 화면에서 `syncApplicantMails` 트리거를 삭제해 더 이상 지원자 추이 데이터가 쌓이지 않게 할 수 있습니다. 이미 생성된 `지원자_추이` 탭은 이 업데이트가 변경하거나 삭제하지 않습니다.

## 3. GitHub Secret 등록

저장소의 `Settings → Secrets and variables → Actions`에서 다음 Repository Secret 두 개를 등록합니다.

- `SHEET_API_URL`: Apps Script의 `/exec` URL
- `SHEET_API_TOKEN`: Apps Script에 등록한 `API_TOKEN` 값

게임잡 계정 Secret과 Gmail 수집은 더 이상 사용하지 않습니다. 지원자 이름과 전형 단계는 연동용 시트에서만 읽습니다.

## 4. 최초 실행

1. 저장소의 `Actions` 탭을 엽니다.
2. `Sync recruiting data and deploy Pages`를 선택합니다.
3. `Run workflow`를 실행합니다.
4. 작업이 완료되면 `Settings → Pages`에 대시보드 주소가 표시됩니다.

이후 매시간 7분에 자동으로 공고와 지원자 현황을 갱신합니다. 시트를 수정한 직후에는 대시보드의 `데이터 다시 불러오기`를 누르면 현재 화면에 바로 반영됩니다.

대시보드는 지원자 추이 데이터를 읽거나 배포하지 않습니다.

## 5. 즉시 불러오기 기능 적용

1. ZIP의 최신 `google-apps-script/Code.gs`를 기존 Apps Script 편집기에 전체 덮어씁니다. 이 버전은 `지원자_추이`를 읽지 않습니다.
2. Apps Script 왼쪽 `트리거` 화면에서 `syncApplicantMails` 시간 기반 트리거를 삭제합니다. 이 단계가 끝나야 Gmail 수집도 중지됩니다.
3. `배포 → 배포 관리 → 수정`을 누릅니다.
4. 버전을 `새 버전`으로 선택하고 다시 배포합니다.
5. 기존 `/exec` 주소가 유지되는지 확인합니다.
6. GitHub의 `SHEET_API_URL` Secret은 기존 값을 그대로 사용합니다.
7. GitHub Actions의 `Sync recruiting data and deploy Pages`를 한 번 실행합니다.

`REFRESH_API_URL`, GitHub 개인 토큰, Cloudflare Worker는 사용하지 않습니다. 즉시 불러오기는 읽기 전용이며 시트의 탭·행·셀을 생성하거나 수정하지 않습니다.

## 브라우저 메모

- `전형·메모 편집`에서 메모와 해당 공고가 사용하는 전형 단계를 설정합니다.
- 아트 계열은 `온라인 과제`, 개발 계열은 `코딩테스트`를 기본 추천합니다.
- 현재 지원자가 있는 단계는 설정에서 해제해도 누락 방지를 위해 계속 표시됩니다.
- 내용은 브라우저의 로컬 저장소에만 저장됩니다.
- Google Sheet나 GitHub에는 기록되지 않습니다.
- 다른 PC·브라우저와 공유되지 않으며 브라우저 데이터를 지우면 삭제됩니다.

## PDF 채용 리포트

- 메인 화면의 `리포트 생성하기`를 누르면 표지, 전체 채용 지표, 전형별 인원, 오퍼·입사 예정 목록, 프로젝트별 공고·배경·진행 현황을 한 화면 미리보기로 확인합니다.
- `PDF 저장`을 누르고 인쇄 창에서 `PDF로 저장`을 선택하면 파일로 보관할 수 있습니다.
- 프로젝트별 목표 TO는 공유 TO를 중복 계산하지 않으며, 직무와 지원자 진행 현황은 각 공고별로 표시합니다.
- 브라우저 메모도 리포트에 포함합니다.

## 기존 공개 사이트에 연결

기존 `gpt-final` 저장소의 Actions 변수 `RECRUITING_DASHBOARD_URL`에 새 GitHub Pages 주소를 입력한 후 기존 사이트를 다시 배포합니다.

## 로컬 확인

```bash
npm install
npm run dev
```

로컬에서는 `public/data/dashboard.json`의 기본 빈 데이터를 표시합니다. 실제 데이터는 GitHub Actions 실행 과정에서 생성됩니다.
